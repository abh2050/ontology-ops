## Also covered
- **Owner decision 4 scenario.** A split order is invisible to both operators. Neither operator can submit it (404), the reviewer cannot propose (403), and no case ever contains it (`test_split_order_can_never_become_a_case`).
- **Independent reviewer scope.** A reviewer without scope over the target gets 404 and no case (`test_reviewer_must_independently_hold_scope`).
- **Stale evidence at execution.** A source correction changes the seller's evidence, so the proposal is marked stale and the API returns 409 (`test_stale_evidence_at_execution`).
- **DraftCustomerUpdate.** It inserts an `internal_drafts` row only. No case is created, and there is no recipient, email, or phone column.
- **Demo drill.** The worker crashes after writing `ready` and before acknowledging SQS. After redelivery the job is acknowledged without new model calls, one proposal is created, and one case results.
- **Atomic approval.** Approval inserts the case, sets the proposal to executed, and appends an audit event in one transaction. The audit sequence is `proposal_created` then `case_created`.
- **Proposals.** Creation is idempotent per job. It re-validates scope, ontology version, eligibility, and the snapshot hash at creation.

## Design notes
- Approval runs in one API-role transaction. It locks the proposal row (`FOR UPDATE`) and takes `pg_advisory_xact_lock` on batch|target. It re-checks the reviewer's role and independent scope, the revision, the ontology version, the proposer's current scope, eligibility (recomputed under the proposer's scope, so the snapshot hash stays comparable), and any existing equivalent case. `UNIQUE(proposal_id)` on cases and drafts backs up duplicate safety.
- Stale outcomes mark the proposal `stale`, write an audit event, and return 409. The transaction still commits, so the history is kept.
- The API role cannot lock job rows, so proposal creation is serialized per job with an advisory lock.
- Endpoints: `POST /api/jobs/{id}/proposal`, `GET /api/proposals[?state]`, `GET /api/proposals/{id}`, `POST /api/proposals/{id}/decision`, and `GET /api/cases`. Reviewers see only proposals whose target and every selected order they hold.
